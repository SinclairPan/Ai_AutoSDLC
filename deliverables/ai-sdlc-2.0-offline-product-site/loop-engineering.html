Loop Engineering

让 AI 开发任务，从明确需求走到可验证完成

Loop Engineering 不是固定流程图，而是一组有输入、有状态、有证据和退出条件的反馈闭环。 缺口回流，失败可恢复，满足条件后才允许 Close 或 Freeze。

查看一个 Loop 如何收敛

Governed lifecycle

正式 WorkItem 路径

普通对话可以启动澄清，但任意聊天输入不会自动成为完整 WorkItem。只有显式进入这条路径， 才会建立受治理的生命周期、身份、状态与关闭证据。

Init / Adopt → WorkItem → Requirement → Design Contract → Implementation → Frontend Evidence（按需） → Local PR Review（按需） → Close

Minimum protocol

七步最小协议

  1. 接收明确目标与输入，建立 Loop 身份。
  2. 不依赖聊天记忆，从项目工件重算当前状态。
  3. 输出缺失信息、停止原因与唯一下一步动作。
  4. 执行或复核前冻结 input_digest 与只读复核快照。
  5. 将 Findings 回流原 Writer；Reviewer 不修改候选。
  6. 定向修复后，只允许基于重新绑定输入进行最多一次复审。
  7. Freeze / Close 前重建输入；任何绑定输入漂移都拒绝关闭。

State reference

状态比总结更可靠

状态 系统含义
needs_user 缺少决定或输入
needs_fix 候选必须修改
needs_review 独立验证待完成或结论不确定
closed 新鲜绑定证据满足 Close 合同

Recovery contract

失败不会被改写成成功

  1. 发现缺口
  2. 明确状态
  3. 用户 / Writer / Reviewer 行动
  4. 重新计算工件与状态
  5. Close 或保持未关闭

输入发生漂移后，旧证据立即失效；重新绑定前拒绝复用。系统会基于当前工件重算状态， 不让过期结论穿过 Freeze 或 Close。

Loop workspace

选择一类 Loop，查看它如何收敛

这是一张机制工作台，不是运行统计或虚构后台。

01

Requirement Loop

把模糊想法变成可复核的目标、范围与验收标准；信息不完整时停在 needs_user。

当前输入

目标、范围、验收标准、角色、风险与待澄清问题。

当前状态

needs_user 表示仍需明确决定，不用模型熟悉的答案补空白。

反馈动作

输出缺口和唯一下一步，由用户补充范围、约束或授权。

Close / Freeze 条件

当前输入已经复核且未漂移，才允许 Requirement Freeze。

可检查工件
  • objective
  • acceptance criteria
  • input_digest
  • review_snapshot

02

Design Contract Loop

检查需求是否映射成可执行任务，重点是接口、边界与验证覆盖，不以文档长度判定完成。

当前输入

冻结需求、接口与数据边界，以及已确认的技术栈和实现约束。

当前状态

needs_fix 表示设计覆盖或任务映射仍有必须修复的缺口。

反馈动作

Findings 回到原 Writer，定向补齐设计合同并重新生成覆盖报告。

Close / Freeze 条件

工件彼此一致、覆盖关键边界且复核输入保持不变。

可检查工件
  • spec.md
  • plan.md
  • tasks.md
  • coverage / report

03

Implementation Loop

管理 required tasks、进度与验证；任务做完后进入独立复核，而不是直接自报完成。

当前输入

当前候选、required tasks、允许修改的范围与验证命令。

当前状态

blocked task 进入 needs_fix；required tasks 完成后进入 needs_review。

反馈动作

原 Writer 修复同一候选，重跑受影响的测试、lint、build 与项目验证。

Close / Freeze 条件

required tasks 完成，当前候选证据通过，并完成独立复核。

可检查工件
  • required tasks
  • verification-evidence.json
  • test / lint / build

04 · 按需

Frontend Evidence Loop

让真实浏览器结果进入交付状态；显式 skip 只代表本次未执行，不冒充浏览器验收。

当前输入

可加载 browser entry、目标页面、交互路径与证据身份。

当前状态

needs_review 表示浏览器证据仍待独立核验或结论不完整。

反馈动作

定位页面或交互问题，由原 Writer 修复后重新运行 Browser Gate。

Close / Freeze 条件

当前页面、交互和错误证据结构完整、身份匹配且没有时效漂移。

可检查工件
  • browser entry
  • interactions
  • console / page errors
  • screenshots

Cross-stage rail

提交前跨阶段复核（按需）

Local PR Review 是独立本地只读 Reviewer 执行的提交前终审，不是与四类 Loop 同构、永远必跑的第五阶段。

  1. Review Pack绑定 Git range、暂存区、工作区或补丁。
  2. Findings检查跨阶段回归、修复与当前验证证据。
  3. fix / rerun原 Writer 修复候选并重跑必要验证。
  4. final report无未解决 Finding 才生成最终报告，否则保持未关闭。

Loop 的价值不是不停重试，而是在每次反馈后知道该继续、该修复，还是该停下。
