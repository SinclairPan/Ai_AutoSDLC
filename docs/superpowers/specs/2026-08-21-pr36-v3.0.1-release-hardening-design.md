## 1. 目标

在不减少 12 条新用户路线、不建设新安装平台、不改变 AI-SDLC 核心运行时语义的前提下，关闭两个发布阻塞项：

1. Linux 在线、主机缺少 Python 时，公开的通用 `linux-amd64` 承诺大于 Debian 12 的真实证据；
2. Windows Python bootstrap E2E 在隔离 PATH 重组后仍可能命中宿主机 `%SystemRoot%\py.exe`，导致测试不能证明 Python 仅由模拟 package manager 创建。

完成后，PR #36 仍是 v3.0.1 比赛最终补丁版；不借本次修复扩张 self-update、签名、原子安装、发行资产或新平台范围。

## 2. 决策

采用 A+：精确 Linux 支持矩阵 + fail-closed 在线安装器 + hermetic Windows harness。

明确拒绝：

- 在线下载新的 portable Python、`uv` 或第三方 runtime；
- 自动添加 PPA、EPEL、deadsnakes 或其他第三方软件源；
- 建设 apt/dnf/yum 的通用发行版适配层；
- 改动五 Loop、review kernel、Local PR exact-tree、自更新协议或发布资产格式；
- 用 mock-only 证据替换真实 Debian、Ubuntu 或 Windows runner 证据。

## 3. 12 路线合同

12 个 route ID 和七阶段标记保持不变：

`2 项目状态 × 2 安装渠道 × 3 操作系统 = 12`

Linux 路线按渠道区分支持边界：

### 3.1 在线路线 3 / 9

- 已检测到可用 Python 3.11+：现有 Linux AMD64 调用兼容路径不变，不新增发行版阻断；该路径属于用户提供运行时的兼容行为。
- 未检测到 Python 3.11+：正式自动 bootstrap 仅认证 `Debian GNU/Linux 12 (bookworm) + amd64/x86_64 + glibc + bash + Debian 官方仓库`。
- 其他发行版、版本、架构或 libc：在安装器执行任何 Python 包安装、venv 创建、PATH 修改和项目写入前非零退出；用户手册的 CA/curl/Git 准备步骤仍按其独立合同执行。错误输出明确说明 Debian 12 边界，并引导使用包含 bundled Python runtime 的 v3.0.1 Linux 离线路线。

### 3.2 离线路线 6 / 12

- 继续使用现有 `ai-sdlc-offline-3.0.1-linux-amd64.tar.gz` 及 bundled Python runtime。
- 不新增资产、下载源或 runtime 构建方式。
- 不用在线 Debian 证据推导离线兼容性；保留现有离线构建、校验和 release-artifact smoke 证据。

### 3.3 用户可见表述

- README 选择器和用户手册必须说明：Linux 在线无 Python 自动安装的认证环境为 Debian 12 AMD64；其他无 Python Linux 主机选择 bundled-runtime 离线路线。
- 不再使用可被理解为“所有 Linux AMD64 均能由在线安装器自动安装 Python”的无条件表述。
- route anchor、制品名和机器可验证 platform ID 继续为 `linux-amd64`，避免破坏既有消费者。

## 4. Linux 安装器设计

`install_online.sh` 保持现有公共调用：

```text
install_online.sh [venv-path] [--add-to-path]
```

### 4.1 判定顺序

1. 先执行现有 `pick_python`；若 Python 3.11+ 可用，直接继续，避免破坏既有兼容路径。
2. 仅在 Python 不可用时读取 `/etc/os-release`、`uname -m`，并用 `getconf GNU_LIBC_VERSION` 核对 GNU libc。
3. 只有以下条件全部成立才执行 apt bootstrap：
   - `ID=debian`
   - `VERSION_ID=12`
   - 架构规范化为 `amd64/x86_64`
   - GNU libc
   - `apt-get` 可用
4. 其他情况返回稳定非零状态，且不执行 Python package-manager bootstrap、不创建 venv、不修改 PATH。
5. Debian 12 路径继续安装已验证的 `python3.11`、`python3.11-venv`、`python3-pip`，再执行第二次 `pick_python` 和现有安装流程。

### 4.2 错误输出

unsupported 环境必须输出：

- 当前识别到的 distro/version/arch/libc；
- 在线零-Python自动安装只认证 Debian 12 AMD64；
- v3.0.1 Linux 离线包的精确制品名和用户手册路线 6/12；
- 当前安装器未执行 Python 包或 AI-SDLC 安装。

不自动修改软件源，不把 `apt` 失败包装成成功，也不要求普通用户手工建立 venv 或 pip 环境。

## 5. Windows harness 设计

本项只修改测试 harness 和合同测试，不再修改 `install_online.ps1` 产品发现逻辑。

### 5.1 根因

当前 isolated Machine PATH 包含 `%SystemRoot%` 根目录。安装器重组 Machine、User、Process PATH 后，宿主机 `C:\Windows\py.exe` 可以排在 fake `py.cmd` 之前。安装虽成功，但测试可能错误接受预装 launcher。

### 5.2 Hermetic PATH

- 在隔离前保存 Machine、User、Process PATH 和 PowerShell 绝对路径。
- isolated Machine/Process PATH 只保留：
  - `$shimRoot`
  - `%SystemRoot%\System32`
- 不包含 `%SystemRoot%` 根目录。
- 启动安装器前断言：
  - `Get-Command py -All` 只能解析到 fake failing shim；
  - `python` 不可解析；
  - `where.exe py` 不得返回 `%SystemRoot%\py.exe`。
- winget 与 choco 两次 replay 各自证明：安装前无 Python、恰好一次 package-manager install、安装后 runtime 可用、venv/CLI 为 3.0.1。
- `finally` 无条件恢复 Machine、User、Process PATH；失败时保留输出和事件证据。

## 6. RED -> GREEN 验收

### 6.1 Linux

先写并观察以下 RED：

1. 删除在线路线 3/9 的 Debian 12 支持边界，validator 仍错误通过；
2. Ubuntu 22.04、无 Python、apt 可用时，安装器仍尝试安装 `python3.11`；
3. Debian 12、无 Python时，必须继续完成真实 apt bootstrap；
4. 修改后 route marker 仍必须精确为 12，七阶段顺序不变。

GREEN 必须证明：

- Debian 12 × new/existing：从无 Python、Git、curl 的真实容器完成安装、init/adopt、版本和业务文件保护；
- Ubuntu 22.04 × new/existing：在 Python 包安装和 venv 创建前明确 fail-closed，并指向离线路线；
- 用户已提供 Python 3.11+ 的非 Debian Linux 兼容路径不被新增 distro guard 阻断。

### 6.2 Windows

先增加会在当前实现上失败的合同断言：isolated persistent PATH 必须让 shim 优先并排除 `%SystemRoot%` 根目录。

GREEN 必须证明：

- winget/choco replay 均不能解析到宿主 `py.exe` 或预装 Python；
- 两个 package manager 分支均通过正式 Windows User Guide E2E；
- Machine、User、Process PATH 在成功和失败后均恢复。
